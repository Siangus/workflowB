## Purpose
Review architecture documentation for utility, correctness, completeness, consistency, and stakeholder usability.

## Trigger
An architecture package is proposed, baselined, or changed materially.

## Procedure
1. Identify reviewers and their intended uses.
2. Review views, catalogs, mappings, interfaces, behavior, rationale, and glossary.
3. Check for conflicting definitions, missing elements, ambiguous notation, and stale assumptions.
4. Record findings and update the package.

## Checks
- Reviewers can answer their intended questions.
- Findings have owners and closure evidence.
- Documentation matches the current architecture.

## Anti-patterns
- Proofreading diagrams without evaluating whether they support decisions.
- Accepting documentation because the author understands it.
