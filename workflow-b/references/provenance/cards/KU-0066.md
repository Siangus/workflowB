## Purpose
Coordinate persistence changes, prevent duplicate in-memory identities, and control data loading inside a business transaction.

## Trigger
A business operation changes multiple persistent objects or repeated loads create consistency/performance problems.

## Procedure
1. Define business transaction scope.
2. Track new, dirty, and deleted objects.
3. Use identity mapping where object identity matters.
4. Apply lazy loading only where access patterns justify it.
5. Test commit, rollback, duplicate loading, and query count behavior.

## Checks
- All intended changes commit or roll back coherently.
- Lazy loading does not create unbounded query cascades.

## Anti-patterns
- Hiding database calls inside arbitrary property access.
- Using a unit of work without a clear transaction boundary.
